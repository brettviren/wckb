# wckb: developing the `kb` tool

This repository is the `kb` tool. It is *not* a knowledge base. The builtin
LLM policy for stores (instruction snippets, skills, hooks) is in
`src/kb/data/policies.json`, `src/kb/data/policies/` and
`src/kb/data/skills/`. `kb policy enact` writes it into each store's
target.

Terms are defined in `docs/glossary.md`. Use them in code (names, help
texts, messages) and docs; when you introduce or rename a concept, update
the glossary in the same change.

Open design questions live in `docs/questions.md`. When a change settles or
raises one, update that file.

Read `docs/design.md` before changing behavior. `docs/plan.md` says what's
in scope.

## Layout and layering

- `cli.py` parses arguments, calls logic modules and renders through `ui.py`.
  No data processing goes in either. Every subcommand with required
  arguments shows its help when given none.
- The command tree: everyday verbs at the top, then one family per thing
  (a glossary noun: `kb item`, `kb edge`, `kb inbox` ...); see "The command
  line" in `docs/glossary.md`. Put a new command in the family of the thing
  it acts on, and name it for what it does, not for the format or tool.
  Top-level sections are `cli.SECTIONS`; a family's listing order is its
  `order`. After changing commands run `uv run python tools/gen_cli_doc.py`
  (a test checks `docs/reference/cli.md`).
- The store is one SQLite file per store: `db` (DDL, guard triggers,
  transactions, the network-filesystem guard) and `items` (`Store`: items,
  blobs, events, settings, query tables kept in step on every write).
  Item JSON stays validated by JSON Schema on every write.
- Logic modules: `items` (model, digest, `Store`), `authoring` (new/add/supersede),
  `edit` (set, renditions, content, checkout/checkin), `locations` (location
  sources: db, cas, url, local, asset, datalad), `assets` (assets, bindings, asset
  sources), `sources` (source items: types, guessing, adding), `datasets`
  (DataLad: datasets as source items, clones, content), `content` (placing content, hashing, fetch, verify), `checks`
  (consistency scan), `lint` (advice), `doctor` (remedies: diagnose and fix
  common problems), `status` (the store at a glance), `graph` (staleness, stamping), `build` (views),
  `query`/`search`/`embed`/`context`, `transforms`, `fair` (data describe and
  export), `migrate`,
  `scaffold`, `federation` (neighbors) and `federated` (cross-store
  queries), `transfer` (knowledge sets, atomic transfers, multi-path
  reconciliation), `bundle` (bundles, inbox, reviews), `render` (view models
  and formatters for people), `exchange` (bundle pull requests),
  `push` (candidates, push, pull, obtain), `sync` (twins), `policy` (policy elements, enactment, autonomy), `hooks`
  (Claude Code hook entry points), `githooks` (git hooks for exchange repositories), `forge`
  (GitHub/Gitea/Forgejo/Gogs APIs) and `secrets` (secret specs).
- Schemas: hand-written JSON Schema in `src/kb/schemas/v<N>/`. After
  changing them, run `uv run kb item schema --markdown > docs/reference/schema.md`
  (a test checks this). Additive changes bump `schema.REVISION`. Breaking
  changes bump `MAJOR` and add a migration in `migrate.MIGRATIONS` with a test.
- Builtin policy elements live in `src/kb/data/`. Bump an element's
  `version` in `policies.json` whenever its text changes.

## Conventions

- When user testing turns up a problem kb could detect or repair, add a
  remedy to `doctor.py` (diagnosis, and a fix if one is safe) with a test,
  and list it in `docs/howto/health.md`.
- `uv sync`, `uv run pytest`, `uv run kb`.
- Tests use real temporary stores (and git repositories where git is
  involved; see `tests/conftest.py`). Don't mock internals. Fakes are fine at external
  boundaries (the embedding service).
- Keep imports in `cli.py` lazy; LLMs call `kb` often and start-up time
  matters.
- Errors meant for users are `KBError`, and the CLI shows them as one line.
- Never print or log a resolved secret. Use `secrets.mask` for display.
- Tests run inside Claude Code sessions. `tests/conftest.py` clears the
  agent environment variables. Tests of autonomy set `KB_AGENT=1`
  explicitly.

## Working with the knowledge base

A knowledge base (KB) of people and their LLM sessions. You are one of its
writers. Other LLMs will read what you write, often without the context you
have now, so write for them.

A store is one SQLite file (`kb.sqlite`) holding knowledge items: JSON
objects validated by JSON Schema (`kb item schema KIND`). Everything goes through
the `kb` command (`kb --help`, `kb COMMAND --help`). Never open the
database directly.

- Kinds of item:
  - `observation`: an assertion, such as "run 1234 was noisy";
  - `document`: a paper, slides or a note;
  - `dataset`;
  - `config`;
  - `snapshot`: an extract from the conditions DB, elog, ...;
  - `software`;
  - `topic`: a synthesis page;
  - `view`: a recipe for HTML/PDF;
  - `person`;
  - `policy`: guidance like this;
  - `kset`: a selection of items, the unit of transfer.
- `kb status` shows the store at a glance and what needs attention;
  `kb doctor` diagnoses problems, and `kb doctor --fix` repairs them (within
  the `curate` autonomy).
- Find things with `kb context`, `kb ls` and `kb search`; read one item with
  `kb show ID` (`--format llm` for its full content). Its history is `kb log ID`.
- Content is held in *renditions*: small text in the store, large files in a
  content store or at a URL, always with a sha256. Get a file with
  `kb rendition path ID#NAME`, and text with `kb item content ID`.

Rules:

1. **Primary items are append-only.** The store refuses changes to what an
   observation, document, dataset, config, snapshot or software item
   asserts. To correct one, use `kb item supersede ID`; to withdraw one, use
   `kb item retract ID`. You may change `status`, `subject`, `tags`, `summary`,
   `evidence` and `related` with `kb item set`.
2. **Attribute every assertion** (`--by`, `--how`, `--when`). If you inferred
   it yourself: `--by claude --how "inferred from <what>"`.
3. **`verified` needs evidence** from an authoritative source. Hearsay is
   `unverified`, and a model's reading of a figure is not evidence.
4. **Write the summary for the next LLM:** one to three sentences, not the
   title again.
5. **Set `subject` and `valid`.** Reuse subject paths (`kb ls --subjects`).
   Give run ranges or time windows whenever the claim has them.
6. **Cite in topics:** `[ID]` for every factual sentence, with every cited
   item in `derived_from`. Then run `kb item stamp ID`. Change a topic's text
   with `kb item content ID --file page.md`.
7. **Store data and scripts, not pictures of plots.** `kb add` decides where
   large files go.
8. **Respect `access`.** Never move content to a more open level than its
   inputs.
9. **Run `kb check` when you finish a batch of changes.** Mention `kb lint`
   findings.

## KB habits for every substantial request

Treat the KB as your working memory for this scope. The point is that the
human doesn't have to remind you.

- **Before answering**, when the request touches facts about this
  project, its data, its decisions or its history, run
  `kb context "<key words or subject>"` (add `--reach 1` for neighbor stores
  when the local store is thin). Use what it returns and cite item IDs.
  If a "KB may be relevant" note was injected into the prompt, follow it up
  only if it is relevant.
- **While working**, when a fact, decision, number, pitfall or result is
  established that someone would want later, file it in this store. Follow
  the `capture` autonomy:
  - `auto`: file it with `kb new` (or `kb add` for files) and say so in one
    line;
  - `ask`: propose the item in one line and file it if the human agrees.

  Prefer few, specific, attributed items over many vague ones, and don't
  file what is already there (`kb search` first).
- **When something you find contradicts the KB**, say so and offer
  `kb item supersede` (see kb-correct). Don't silently work around it.
- **Mark what deserves a wider audience** with `kb item set ID --add tags=promote`.
  Promotion itself is a separate review (kb-promote).
- Keep it light: a lookup or a filing is one command. Don't narrate KB
  mechanics at length.

## Neighbor stores and knowledge transfer

This store is linked to others. The table above lists them with what you may
do. The relation of each link sets how knowledge moves by default:

| link | push (here → there) | pull (there → here) |
|---|---|---|
| `up` (broader) | `select` | `all` |
| `down` (narrower) | `all` | `select` |
| `peer` | `select` | `select`, into the inbox for review |
| `twin` (a copy of this store) | `kb sync` | |

- **Reading.** Neighbors are references: `kb context ... --reach 1`,
  `kb search ... --reach 2`, `--in NAME`. Cite items from other stores with
  the store name.
- **References are store-independent.** An item may cite one that isn't
  here. `kb check` warns `dangling`, and `kb pull ID` (or
  `kb pull --dangling`) fetches it from the nearest store that has it.
- **Transfers move knowledge sets.** A set is shallow (just the named items)
  or deep (also everything they reference). `kb push --to N IDS` makes the
  set for you, and `--deep` follows references. A transfer is atomic, and
  it's refused if an item conflicts with what the receiver holds.
- **Landing.** A push lands per the edge: `apply` (straight in), `inbox` (a
  bundle the receiver reviews) or `pr` (a bundle proposed by pull request).
  Incoming bundles are reviewed with skill kb-review.
- **Writing.** You write to this store. Knowledge leaves only through
  `kb push`, as the outcome of a promotion review (skill kb-promote).
- **Autonomy.** For `push`, `pull`, `accept` and `merge`, follow the table:
  - `never`: give the human the command;
  - `ask`: get approval and pass it with `--approved "<their words>"`;
  - `auto`: act, then report.
- **Never relabel access** (`--access`) without the human saying so.
