# 0005. Topical notes: kept where they are made, found through kb

- **Status:** accepted 2026-11-09. Builds on [0004](0004-artifacts.md)
  (artifacts) and [0003](0003-datalad-sources.md) (DataLad sources).
- **Settles:** where notes live, what is standard about them, how existing
  work areas and claude.ai artifacts get in (questions AR7–AR9).

## The need

People (and their LLMs) write *topical notes*: technotes, explainers,
research summaries, log books. They are more than a paragraph and less than
a paper, there are many, and they are made next to the work they
summarize: scripts, run output, builds, git clones. They are *living*: they
are regenerated when the study changes. Yet people want to browse, search
and share them as one collection, and to see how they changed.

Three pressures pull apart:

- **In place:** a note is regenerated by scripts and workflows beside it, so
  it should stay there.
- **Together:** the collection should be searched and browsed as one,
  whatever made each note.
- **Not everything:** work areas hold terabytes of data and build products
  across hundreds of projects. A note repository that contains them is
  untenable, and DataLad over all of them is too heavy.

## Decisions

1. **Centralize the index, not the files.** A note stays in its work area;
   the store holds its item: an artifact (a `document` of doctype
   `technote`, `demo` or `notebook`), with summary, subject, extracted text
   and the items it presents. Nothing about the note moves. This is 0004's
   design, now applied to work that already exists.

2. **Only the note's directory is a dataset,** not the work area above it.
   `kb artifact adopt DIR` makes DIR an artifact workspace around what is
   there: nothing is moved or changed. The work area's three tiers are
   treated differently:

   | tier | example | treatment |
   |---|---|---|
   | important, versioned elsewhere | git clones | ignored by the dataset; their remotes and HEAD noted in `.kb-artifact/repos.json`, refreshed by `finish` and carried in the process record |
   | semi-important | run scripts, the note, small results | in the dataset |
   | ephemeral | `*.o`, `*.so`, `*.a`, `build/`, an install prefix, LaTeX leftovers | ignored (`artifacts.BUILD_IGNORES`; add with `--ignore` or the setting `workspace.ignore`) |

   Nested clones are not made subdatasets: active clones are dirty most of
   the time, and `datalad run` needs every subdataset clean.

3. **Annex stays out of the way.** Locked, read-only annexed files make
   jobs fail that legitimately write to them. A workspace's dataset
   therefore annexes only files above a size (`1MB`, setting
   `workspace.largefiles`); everything smaller is plain git. What is annexed
   is *unlocked* (`annex.addunlocked`): an ordinary writable file, not a
   link to a read-only object. The hash backend is SHA256E, which kb can
   use as the file's digest. `kb doctor` (`workspace-annex`) sets
   `annex.addunlocked` in a workspace clone that lacks it, since git config
   does not travel with a clone. Cost: a second copy of annexed content, only
   for what is large.

4. **No required source format, one standard description.** Notes are
   Markdown, org, LaTeX, Quarto (`.qmd`) or HTML, and kb converts none of
   them. What is standard is the *deliverable* (a PDF, or an HTML page that
   works as a unit) and a small **sidecar**, `note.toml` (or
   `NAME.note.toml`) beside the note: title, summary, subject, creators,
   date, doctype, tags, identifiers, the items it presents (`inputs`), and
   for the record its `source` files and `build` command. One description
   for every format, instead of a front-matter convention per format.
   `kb artifact finish` reads it; options override it. An agent that makes a
   note writes the sidecar. In a directory that has notes, new ones use the
   format already there; otherwise the person says.

5. **Claude artifacts are ingested, and their URL kept.** A page published
   at claude.ai/artifact is private by default and tied to a login, can
   change under the same URL, and can go away, so an item must not depend on
   it. In a Claude session the `Artifact` tool reads it (a single page is
   saved as a file; a multi-file one with `read` of its `paths`); the files
   go into a workspace, and `kb artifact finish PAGE --doctype demo
   --published-at URL` registers it, with the URL and the artifact's ID as
   identifiers. A republish is read again and finished again: a new version
   supersedes the old. A `git-annex-remote-claude` is not built: there is no
   public API or token to build it on that we know of (AR9).

## Consequences

- Staleness covers only items. A note regenerated from a file in the work
  area has no item to go stale; capture the data as an item (`kb add`) and
  cite it (AR8).
- Adoption is one command per topic, repeatable; finding the notes in a
  work area (`kb artifact scan`) is left open (AR8).
- Plain-git workspaces (no annex, no DataLad) would suit areas that hold
  nothing large; open (AR7b).
